# 最终一致性 Eventual Consistency

## 定义

最终一致性并**不保证**在分布式系统中每次进行读都可以读取到最新的值(recall:分布式系统中不同节点数据副本需要同步，在**不同节点进行本地读并不能保证每个时刻值都是一致的**)，但最终一致性保证在分布式系统中**不进行新的写操作**时，经过**一定时间**，这个分布式系统**最终**会达到所有**数据副本一致**（但并没有保证一定时间是多久）。

## 最终一致性实现

### Feature

#### 写操作

* 写操作允许直接在**任何一个节点中本地进行**，客户端向分布式系统中发起写操作时直接在**距离客户端最近的节点**进行写，操作**结束后再传播**数据更新到其他节点（**异步数据复制**）
* 需要解决**写-写冲突**以及**因果性冲突**

#### 读操作

* 读操作允许直接在**任何一个节点的本地进行**，直接返回节点本地的数据。

#### Update Function 更新函数

* 将某一时刻下节点中的所有数据构成的整体视作该节点中数据的状态，在分布式场景下，各个节点初始状态相同（都是空），在各自进行本地的写之后，各个节点之间的状态就变得不一致，所以最终需要合并这些状态。

* 节点在进行本地写操作之后，再将写操作传播至别的节点。如果每个节点收到的写操作合集是相同的，那么只需要对这一系列的写操作决定一个全局统一的顺序（即在每个节点中对这些写操作进行排序都能得到一个相同的写顺序），就能保证从一个相同的初始状态，按照相同的顺序应用写操作序列，最终得到的状态也是相同的。

* 为了保证写操作对数据状态更新的语义，并不能够直接用新值对旧值进行覆盖。

  > eg. 在分布式场景下存储一个向量[x~1~,x~2~,x~3~]。
  >
  > 节点1中客户端发出请求要在向量末尾添加一项A，向量变为[x~1~,x~2~,x~3~,A]。而节点采用的数据更新语义是直接覆盖
  >
  > 客户端看到追加A的请求成功后，又发出请求追加B，而收到写请求的是节点2，若此时节点2还未同步到[x~1~,x~2~,x~3~,A]这个数据，还是旧的数据[x~1~,x~2~,x~3~]，那么最终节点2得到的结果会是[x~1~,x~2~,x~3~,B]
  >
  > 当各自传播本地数据更新进行同步的时候，节点1收到的是将向量更新为[x~1~,x~2~,x~3~,B]，节点2收到的是将向量更新为[x~1~,x~2~,x~3~,A]，然而在客户端看来实际想要的语义是将[x~1~,x~2~,x~3~]更新为[x~1~,x~2~,x~3~,A,B]

  为了避免上层要求的语义与分布式系统内部数据更新语义的不一致，可以由上层提供一个Update Function，当进行写操作的时候，并不是直接将数据进行覆盖，而是应用Update Function来进行数据修改，而Update Function保证上层需要的数据更新语义。

  > eg. 希望数据更新是追加而非覆盖的语义，就可以提供一个类似于Append操作的Update Function

  对于相同的起始状态，只要对于相同顺序的写操作，逐个应用Update Function，能保证最终的状态一致并且与用户预期的数据操作语义一致。

#### Update Log	更新日志

每个节点存储一个**更新日志**，进行本地写操作时，将其存入到**更新日志**中，为了保证数据最终一致性，需要将数据更新操作**转发**到别的节点，其他节点也将其存入到**修改日志**中，于是每个节点最终的修改日志中的内容是一致的，只是顺序可能不同。需要通过**Lamport Clock**来保证每个节点对于修改日志中的操作排序是一致的，即更新操作的全局序唯一。

##### Lamport Clock

根据`CSE-09 Eventual Consistency.pptx`中提到的Lamport算法与原本的Lamport时钟有些许不一致的地方，但是本质是相同的。每个机器都有一个时钟，而这个时钟是跟随现实时间进行自增的。

* 每个节点维护一个自己的时钟 `T`
* `T`会按照某种方式自增(eg.按照现实时间流逝 or 发生一个事件就自增一次...)
* 当节点收到另一节点通信发送来的消息时，消息必须附带上时间戳`T'`，修改本节点的时钟`T = Max (T,T' + 1)`

逻辑时钟不能保证任意两个操作发生时间可比较，因为不同节点中发生的事件可能分配到相同的时间戳，需要附加上Server ID 来定义节点之间的优先级，保证全局中任意两个操作发生的时间戳可以比较。

Lamport Clock最终的形式为 <Logical Clock,Server ID>。

每个节点自己的时钟自增保证了在同一个节点中先发生的事件的时间戳一定比后发生的事件的时间戳小，即单个节点的事件发生一定有序。

修改本地时间戳保证了分布式系统中事件之间的因果性。即当一个节点中发生了一个事件A，其对应的时间戳是T，那么之后其他节点中发生的事件分配到的时间戳必定比T大，那么就保证了如果与事件A有关系的事件发生的逻辑时间必定在事件A之后。

当分布式系统中(注意是整个系统的水平，而不是从单一机器进行考量)，出现了数据写操作，而这个写是先在某个节点写入的，这个节点此时的时间戳就标志了这个写入事件发生的“时间”，当这个写入事件作为日志被放入各个节点的日志时，时间戳不能发生变动。即Lamport Clock修改的是机器中维护的时钟，而不会修改事件发生的时间。

个人认为Lamport Clock按照现实之中的时间来流动并不是一个好的实践，最好是按照原本Lamport描述的意思来，对于节点中每进行一次写入操作将本地的时钟 + 1。

##### Vector Clock

* 每个节点维护一个时钟向量 [C~1~,C~2~,C~3~,...,C~n~]，C~i~表示第i个节点中的逻辑时钟

* 节点本地的时钟按照某种方式自增（eg. 每发生一个新的数据操作进行自增 / 按现实时间流逝自增）

* 节点收到来自另一节点的消息时，消息必须附带时钟向量[C~1~',C~2~',C~3~',...,C~n~']，更新本地时钟向量[C~1~,C~2~,C~3~,...,C~n~]，

  C~i~ = Max( C~i~ , C~i~' +1)

Vector Clock并不能保证全局操作序列中任意两个操作的发生时间可比较，定义的是偏序关系。

#### Rollback&Replay 状态回滚 

如果所有的写操作都不立即执行而是放入日志，进行读操作就会很费事（遍历Update Log以找到对应的写入操作）。出于性能考虑，不仅将写操作记录在**更新日志**中并在**各节点日志**中进行**同步**，同时还在**节点本地**将**写操作执行**，但是会记录节点中数据的**初始状态**。每个节点本地都执行了一系列不同的写操作，所以各个节点之间**数据状态不一致**，但是最终的**更新日志是一致的**（同步 & 有统一的全局序）。各个节点将当前的状态**回滚**到初始状态，然后将**更新日志**中的操作序列按顺序执行即可达到所有节点数据**状态一致**的情况。

如果分布式系统运行很久，与记录的各节点一致的数据初始状态相去甚远，那么进行一次回滚、再更新的成本就会很大。

需要一种方法来阶段性的将日志中的一部分操作进行执行，使得所有节点都一致的初始状态更新，降低回滚、再更新的成本。不会再发生顺序变动的写操作进行应用，并且丢弃这一部分日志。

##### Stable & tentative write

对于日志中的某些写操作，即使日志中增加新的操作记录，也不会改变他们的执行顺序，称之为Stable Write。

> eg.	分布式系统中，假设节点之间都进行过数据更新同步，并且每个节点的逻辑时钟都严格大于*T*,那么意味着更新日志中所有小于*T*的更新记录他们的排序不可能再变化，因为此后任一节点发生新的写入操作，对应的逻辑时钟都大于*T*，也就是说这些更新记录都是Stable Write。

Stable Write之后的所有数据都是Tentative Write，当有节点出现新的写入操作时，它们在日志中的顺序就可能改变。

如何对日志进行截断并重新应用Stable Writes的关键在于如何识别出日志中的Stable Writes。

##### De-centralized approach 去中心化

对于一个时间*T*，满足以下条件时认为逻辑时间小于等于*T*的更新记录都是Stable Writes（不会发生顺序改变）：

* 所有机器的本地时钟严格大于T
* 任意两台机器之间同步更新操作完毕

基于以上观察，可以对于每台机器维护一个结构，记录该机器与所有机器通信后对应机器的时间戳，然后从中选取出最小的一个时间戳*T*，小于等于*T*的更新记录为Stable Writes，可以依此进行回滚、更新。

> e.g. 假设有Server 0 ~ 3，Server 1中记录的最近一次来自其他服务器消息附带的时间戳是 
>
> * Server 0 : 12
> * Server 2 : 14
> * Server 3 : 15
>
> 这意味着上一条来自Server 0的消息时间戳为12，来自Server 2的消息时间戳是14，来自Server 3的消息时间戳是15，那么Server 0的下一条消息的时间戳由于递增必定为13（或≥ 13），Server 2必定为 15 （或≥ 15），Server 3必定为16（或≥16）。所以之后Server 1可能收到的时间戳最小的消息时间戳为 13 ，那么时间戳小于12的日志都可以应用并截断。

但一旦有机器长期离线，去中心化方法就无法实行。

##### Centralized approach 中心化

选定一个Primary Server，负责分发Commit Sequence Number。当一台机器中的Update Log需要对其中积压的Update Log Entries进行截断时，就到Primary Server请求Commit Sequence Number，一个Commit Sequence Number对应于Update Log Entries中一条操作记录，Commit Sequence Number保证全局递增。

当机器需要截断一部分Update Log时，就需要将这部分的所有操作请求Primary Server给每个操作分配一个CSN。由于CSN保证是全局递增，这就使得最终更新顺序在全局是唯一的，只是可能与用户在中途看到的状态不一致，但能保证分布式系统下每个机器最终的状态是一致的。

当一个机器对其Update Log中需要截断的部分日志请求了CSN，其他机器包含同样的操作但CSN未知，其他机器中对应的日志没有截断，因此需要在其他机器与该机器/其他机器与Primary Server进行通信时，把对应操作分配的CSN告知给其他机器，这样子就保证了同一操作在不同机器上最终的CSN是一样的，所以分布式系统中每台机器保证了最终一致性。

#### 异常行为

##### 写写冲突

将每个节点存储的数据看作状态，在一致的情况下，节点之间的状态是一样的，但是当各自经过一系列数据写操作，节点之间的状态变得不一致，所以需要**合并**这些状态。

##### 因果性冲突

如果采用现实时间来标记每一个写操作，不同节点之间出现时间不同步就会导致写操作的因果倒置，导致最终Update Log中的更新日志条目按照时间排序出现因果性错误。

## 事件顺序与时钟（From 《深入理解分布式系统》）

#### Lamport 时间戳 / 逻辑时钟

分布式系统中要做到每个节点的时间完全同步于一个“墙上时钟”是困难的，因为存在着网络延迟等诸多因素，而诸如网络延迟这样的因素存在导致分布式系统中各个节点之间事件发生的顺序会出现乱序的情况，例如在一台机器上执行的数据更新操作序列为Op~1~Op~2~Op~3~，而因为网络延迟等因素数据更新操作到达另一台机器上出现了乱序，顺序变为Op~2~Op~3~Op~1~，所以需要一种不依赖于具体物理时间的决定分布式系统中事件顺序的“时钟”，以保证分布式系统中事件是有序的。

> 分布式系统中的事件包括：进程内部事件、发送消息事件、接受消息事件

Lamport逻辑时钟定义事件之间的发生关系：

* 分布式系统中如果逻辑上事件a发生于事件b之前，记为a → b
* 如果事件a、b在同一个进程之中，事件a发生于事件b之前，则a → b
* 如果事件a是发送一条消息的事件，而事件b是接受这条消息的事件，则a → b
* 如果a → b，b → c，那么 a → c；如果两个事件不存在a → b或者b → a，则认为两个事件是并发的

a → b定义了分布式系统中事件的因果关系，表示事件a直接/间接影响了事件b。根据因果关系，我们只需要保证当事件a确实影响了事件b的情况下，a的时钟必定比b的时钟小即可；而如果事件a与事件b并没有因果关系，我们并不关心这种情况，因为二者既然没关系那么谁先执行都可以，所以此时无需关心时钟。

**Lamport 逻辑时钟**：

* 每个进程都记录自己的逻辑时钟（时间戳），初始为0
* 进程中发生一个事件，就会将自己进程的逻辑时钟加1，*Clock~i~* = *Clock~i~* + 1
* 如果进程 *i* 向进程 *j* 发送一条消息，进程 *i* 先将自己的时间戳加 1 ，即*Clock~i~ = Clock~i~ + 1*，然后将更新后的时间戳附带在消息上发送给进程 *j*，进程 j 更新自己进程的时间戳为 *Max(Clock~i~ , Clock~j~) + 1*

Lamport逻辑时钟保证了存在因果关系的事件之间必定可以通过比较时间戳大小来排序，然而不存在因果关系的事件这个时间戳就没有意义，则对于分布式系统中的操作序列，如果其中存在没有因果关系的两个事件，是无法比较这两个事件之间的先后顺序的，所以单独的逻辑时钟定义得到的是偏序关系而非全序关系，即无法决定出一个全局唯一的顺序。

比如说在节点1中，操作A的逻辑时钟为1，而节点2中操作B的逻辑时钟为1，二者逻辑时钟均为1，无法比较出操作先后，在进行数据复制同步的时候可能出现在节点1中的操作执行序列是 A B，而在节点2中的操作执行序列是 B A，这就会导致**不一致**，因此需要保证一个全局唯一的排序。

因此除了采用逻辑时钟，还需要额外的标识来保证全局唯一的事件顺序，因此在逻辑时钟的基础上额外附加进程编号（or 分布式系统中各个节点的编号），定义出进程（节点）之间的优先级关系，保证无因果关系之间的事件可以利用这个编号来排序。

二者合在一起构成了**Lamport 时间戳** <*Clock*,*Node_id*>

对于事件a与事件b的顺序，由Lamport时间戳进行决定：

* 当Clock~a~ < Clock~b~ 时，认为 a < b
* 当Clock~a~ = Clock~b~ 时，如果 Node_id~a~ < Node_id~b~ ，则认为 a < b（节点编号决定了优先级）

这样子就可以对分布式系统中各个节点的事件得到一个唯一的排序。

#### 向量时钟

向量时钟与Lamport 时钟类似，只不过每一个节点都需要维护一个描述所有节点中时钟的向量。

对于一个分布式系统中包含节点Node~1~,Node~2~,...,Node~n~，对于节点Node~i~中需要维护一个向量[C~i,1~,C~i,2~,...,C~i,i~,...,C~i,n~]，其中C~i,j~表示第 i 个节点中存储的第 j 个节点中的时钟。C~i,i~则是该节点本身自己的时钟。

* 每个进程有自己的逻辑时钟，同时维护一个时钟向量
* 进程中出现一个事件，将自己进程的逻辑时钟 +1（时钟向量中对应项 + 1）
* 进程 i 向进程 j 发送一条消息时，自己进程的向量时钟对应项 + 1，将更新后的本地向量时钟跟随消息一起发送给进程 j ，对进程 j 中的每一项 C~j,k~ = max(C~j,k~,C~i,k~)

对于向量时钟中的事件关系，如果a → b（a 与 b具有因果关系），则

* a的时钟向量中每个项都小于等于b的时钟向量中的对应项，即 C~a,i~ ≤ C~b,i~
* 在b的时钟向量中至少存在一项是大于a的时钟向量中的对应项，即存在C~b,k~ > C~a,k~

向量时钟定义得到的顺序是一种偏序关系，也会存在无法进行唯一排序的并发事件。

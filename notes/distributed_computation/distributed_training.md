# Distributed Training

## 并行化手段

* 数据并行化：将训练数据批量切分，按分批的数据进行并行化计算，最终通过累加汇总。

* 模型并行化：把模型的计算过程进行切分。

* 同步/异步更新：同步更新要求当前迭代所有并行计算完成才可以进行下一轮迭代；异步更新则不要求所有并行计算完成才进入下一轮迭代。

## 数据并行化

### 思想

* 对于可简单通过累加进行合并的计算，可以将数据进行切分。
* 原本的计算图变成可以并行计算的计算图，每个子图在单独的设备上进行计算。
* 子图并行计算完后还需要进行求和汇总。(All Reduce 阶段)

### 瓶颈

在并行计算阶段，理论上切分成N部分数据就可以由N个设备来并行计算，效率提升到原本的N倍，但是最终需要将N个子图的计算结果进行合并。

通过同步的方式进行模型训练，必须保证前一轮迭代全部计算完才能开始下一个迭代，在单次迭代中采用数据并行化方式进行计算，如果其中一个并行的子图计算被很快完成，依然需要等待所有的并行计算完成后进行数据交换、累加汇总才能进入下一轮迭代。

进行累加汇总就必须在所有设备之间进行全量的数据交换，所以最终汇总会成为性能瓶颈。

### 优化目标

* 降低并行计算后数据汇总的开销。

All Reduce包括**数据计算**及**网络传输**，其中计算开销较小，而**网络传输开销很大**，因为需要传输的参数规模很大，因此需要减少网络开销。 

* 减少**单次数据传输的数据量**
* 避免**大量并行的网络数据传输**到同一台设备

### All Reduce方案

#### Parameter Server

##### 思想

* 专门一台机器进行All Reduce的数据汇总累加计算，即为Parameter Server。
* 每台机器计算完毕将对应的参数结果传输到Parameter Server。（网络传输）
* Parameter Server进行累加计算。
* Parameter Server将结果广播到所有机器。（网络传输）

##### 性能估计

假设单个计算节点需要传播的**参数规模是P**，进行**并行计算的节点有N个**

* 每个计算节点O(P)的网络流量，Parameter Server O(P*N)的网络流量
* Parameter Server承担巨大的网络流量

#### Co-located & Sharded Parameter Server

##### 思想

将**每个计算节点**都变成一个“**Parameter Server**”，负责汇总一部分数据。

* 假设每个计算节点的计算结果规模为P，即要向外传播的数据规模是P。

* **将P按照一定规则进行分区**，集群中**N个节点就分成N份**。

* 0号机器负责Partition 0的数据汇总，1号机器负责Partition 1的数据汇总……

* 每台机器将自己的计算结果中Partition *i* 的数据发送给 *i* 号机器

* 0号机器累加完Partition 0的参数后，广播给其他N - 1个机器；

  1号机器累加完Partition 1的参数后，广播给其他N - 1个机器；

  ……

##### 性能估计

假设单个计算节点需要传播的**参数规模是P**，进行**并行计算的节点有N个**

* 每台机器总共需要承担O((N - 1) * P / N)的网络流量（不需要将自己的数据发送给自己）
* 只需要进行两轮通信，**数据收集** & **All Reduce结果广播**，O(1)级别的通信轮数。
* 每台机器接受 N - 1台机器传输来的数据，**O(N)级别的Fan-in**。High Fan-in带来的问题是当大量节点同时向同一个节点传输数据时，会引起网络拥塞问题。

#### De-Centralized All Reduce 

##### 思想

让每个机器自己进行所有参数的累加汇总，而不是由一个中心化的节点进行汇总后再进行广播。

按照一定的“节拍”来发送数据。

以0号机器进行All Reduce为例：

* 1号机器向0号机器发送1号机器的参数计算结果；
* 1号与0号传输完毕时，2号机器向0号机器发送2号机器的参数计算结果；
* 2号与0号传输完毕时，3号机器向0号机器发送3号机器的参数计算结果；
* ……
* 当0号机器收集完毕0~N号机器的并行计算结果时，进行累加汇总，0号机器就得到了这一轮迭代All Reduce后的数据。
* 按照One-by-One的顺序，接着由1号机器开始自己的All-Reduce，0号机器向1号机器发送自己的计算结果……

##### 性能估计

假设单个计算节点需要传播的**参数规模是P**，进行**并行计算的节点有N个**

* 每台机器总共需要承担O（P  *（N - 1））的流量

  （完成自己的All-Reduce需要 N - 1 台机器传来参数，又要向 N - 1台机器传输自己的参数）

* 总共需要 O（P * P）级别的通信轮数。

* One-by-One的方案下，每台机器同时只接受 1 台机器传输来的数据，O（1）级别的Fan-in

##### 通信轮数优化

* 在1号机器向0号机器传输参数时，2号机器可以向1号机器传输参数，同理，3号机器可以向2号机器传输参数……
* 通信轮数由原本的O（P * P）优化为 O（P），但是每台机器需要承担的总网络流量不变。

##### 传输数据量优化

* 采用Sharding的思想，将每台机器中的参数进行分区，每台机器负责一个分区数据的All-Reduce，并且同时按照一定的“节拍”来进行单个Partiion数据在机器之间的传输。
* 每台机器需要维护与另外N台机器的连接，维护连接的开销随着机器数量增长。

#### Ring All Reduce

##### 思想

* Decentralized Reduce，并非由中心化节点进行所有数据的All Reduce后再广播，而是数据在机器之间传递的过程中逐步完成All-Reduce。
* Partition，将一个机器中的参数按照机器规模进行分区，不同的Partition并行地在进行All-Reduce过程。

从单个Partition的角度来看：

* 假设4个节点0、1、2、3，每个节点中数据的Partition 0部分记为 w~0~，w~1~，w~2~，w~3~
* 0号机器向3号机器发送 w~0~，3号机器执行w~0~ + w~3~
* 3号机器将w~0~ + w~3~的结果发送给2号机器（注意，结果的规模与w~0~和w~3~规模是一样的，因为是进行求和操作），2号机器执行w~0~ + w~3~ + w~2~
* 2号机器将w~0~ + w~3~ + w~2~发送给1号机器，1号机器执行w~0~ + w~3~ + w~2~ + w~1~
* 此时Partition 0已经完成 All Reduce，而只有2号机器持有这个结果
* 2号机器将结果传递给1号机器，1号机器接受并进一步传递给0号，0号又进一步传递给3号
* 整个流程数据按照一个环在进行流动并逐步完成All Reduce。

从多个Partition并行的角度来看：

* 0号机器向3号机器发送 Partition 0 数据同时，3号机器在向2号机器发送 Partition 3 数据，

  2号机器在向1号机器发送 Partition 2 数据，1号机器在向0号机器发送 Partition 1 数据。

* 每个Partition的数据并行的在环中流动并逐步完成All-Reduce。

##### 性能估计

假设单个计算节点需要传播的**参数规模是P**，进行**并行计算的节点有N个**

* 每台机器总共要承担 O（2 * （N - 1）* P / N）级别的数据
* 每台机器同时只接受 1 台机器传输来的数据，并同时向另一台机器发送数据，O（1）级别的Fan-in
* 总共需要O（N）轮的通信（对于每一Partition的数据要经历 N 台机器才完成All Reduce，并在环上再流动一轮使得每一个机器持有All Reduce的结果）
* 每台机器只需要与O（1）级别的机器建立连接，即它在环中的前一个机器与后一个机器。

##### 问题

* 对不满足交换律的算子无法使用，显然每一个Partition流过的机器顺序不一样，因此虽然求和的数据是一样的，但是求和的顺序是不一样的。

#### Tree-Based All Reduce

##### 思想

* 将所有机器构建成一棵二叉树，将这棵树倒置获得另一棵树，这样子保证每台机器上的负载均衡。

## 模型并行化

* 当模型参数规模过大以至于无法单独一个计算设备（GPU）将参数全部读入进行计算时，采用模型并行化。

### Pipeline Parallelism

* 模型进行分层，每层（Layer）由一个计算设备负责进行计算。
* 层与层之间形成流水线（Pipeline），每一层计算完的数据传递到下一层进行计算，像流水线一样每一层形成一个计算的阶段（Stage）
* 正向传播计算将从Stage 0到Stage N，反向传播从Stage N到Stage 0，但是数据在某一个Stage进行处理时，其他Stage是空闲的，也就是会出现流水线中的Bubble。为了减少流水线各阶段的空闲时间，将一批要计算的数据（Batch）进行切片。
* Micro-Batching：类似于CPU流水线，将要计算的一批数据分片，同一批数据的不同片在流水线中的不同Stage并行地进行计算，当所有的片在最后一个Stage计算完，则对应的Batch计算完成。

#### Bubble Time Fraction

气泡的数量是由流水线深度决定的，假设流水线深度为*p*，那么气泡数量有 *p - 1* ;

对于一个Micro-Batch前向传播的计算时间为 *t~f~* ;

对于一个Micro-Batch后向传播的计算时间为 *t~b~*；

理想计算时间为 *m × ( t~f~ + t~b~ )*，气泡占用时间为*( p - 1 ) × ( t~f~ + t~b~ )*，m为Micro-Batch的数量，即Batch的分片数

Bubble Time Fraction： *( p - 1 ) / m*

为了减少流水线的额外开销，

* 增加 m ，即对Batch进行更细的切分
* 减少 p ， 即减少流水线深度

对于Micro-Batch切分来说，micro batch的大小有下限，超过下限GPU的计算效率会受到影响，为了减小m，就需要增大Batch的大小，但增大Batch会影响模型收敛。对于流水线深度来说，采用流水线是为了解决参数规模过大的问题，在参数规模非常大的情况下无法减少p。

### Tensor Parallelism

* 将一层中的参数进行分区，每个分区在一个单独的GPU上进行计算，即在同一层引入多个GPU来计算大规模的参数。
* 本质上是矩阵的分块乘法，在多个GPU中分块计算后进行聚合传递到下一层。

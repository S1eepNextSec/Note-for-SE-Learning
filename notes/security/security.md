# Security

## 权限验证

### Case.Timing Attack

根据输入的密码进行校验，若发现不匹配的字符就立即返回，可以根据返回的时间进行密码猜测。如果能够构造出被比对的密码恰好第一位在内存中一个页的末尾，而之后的字符存储在磁盘上的页，尚未被加载到内存中，就可以进行密码第一位的猜测。当第一位输入正确，后续位错误的时候，就会触发Page Fault去磁盘中加载后续的内容，因此执行的时长会大大增加，根据代码的执行时长明显的变化可以逐位猜测密码。

### 哈希

用存储密码的哈希值来取代存储密码明文。

当然存储哈希并不能保证完全安全，假设某个网站后台数据库被黑客攻破，黑客窃取了大量用户账户的密码哈希值。

* 可以对每个用户的哈希值进行暴力破解，尝试用常见的密码逐一哈希，然后将结果与窃取的哈希值进行对比，直到找到匹配的密码。
* 可以预先生成一个“彩虹表”（Rainbow Table），它是一个针对常见密码及其对应哈希值的大型数据库。通过查表的方式，黑客可以快速匹配某些用户的密码，而无需逐一计算哈希。
* 用户可能倾向于选择简单、常见的密码（如 "123456"、"password" 等），这使得更容易通过彩虹表或暴力破解获取这些账户的密码。

### 加盐（Salting）

* 对于每一串密码明文，添加一串随机数，二者拼在一起进行哈希计算。
* 对于同一个密码明文，因为添加的Salt（随机数）不同，所以最终的哈希值不同，打破了明文到哈希值的一一映射。
* 本质上只是增加了攻击的复杂度，如果攻击者能够获取到数据库中每个用户对应的Salt值，那么依然可以进行攻击。

### Cookie

* 用户与服务器之间建立一个会话，避免用户需要频繁地输入密码进行校验
* 将用户名、会话过期时间以及一个服务器方持有的Server_key拼接在一起进行哈希，作为返回给用户的Cookie，之后可以根据用户传来的Cookie识别出用户
* 对于简单的字符串拼接，攻击者可以通过字符串拼接本身的二义性来进行攻击。

### 钓鱼攻击

* 用相似的域名来欺骗用户输入账户&密码。

### 重放攻击

* 攻击者截获能够识别用户合法性的数据，然后通过这个数据来冒充合法用户进行操作。

### 一些安全技术

* Challenge-Response：服务器给用户传一个随机数，用户根据随机数 + 密码进行哈希，将哈希值传输给服务器，因为服务器持有对应的随机数并且知道哈希函数，可以进行解码。可以防御重放攻击/中间人攻击。攻击者只能截获随机数 + 密码的哈希值，无法获取到密码。
* Turn Off-line to On-line：输入用户名，服务器返回某些数据比如说图片以证明不是钓鱼网站。
* Specific Password：对于每个网站用一个特定的密码，比如说 server_name + password
* One-Time Passwords：只使用一次的密码，即使攻击者获取到对应的密码，也无法使用对应的密码来冒充用户。服务器和用户共享一个Secret String，每次使用时根据当前时间以及Secret String进行哈希。
* N-Time Passwords：服务器存储H(H(H(...H(salt + password))))，即n次嵌套的哈希值，客户端每次发送第 n - 1次的嵌套哈希值到服务器，服务器再进行一次哈希，如果匹配则为正确密码，并且将正确密码设置成第 n - 1次的哈希值。就算攻击者截获了第 n - 1次的哈希值，攻击者传递第 n - 1次哈希值到服务器，服务器再进行一次哈希得到的是第n次的哈希值，此时已作废（因为服务器已经将正确密码设置成第 n - 1次的哈希值）。

## Return-Oriented Programming Attack

### 传统ROP攻击

* 通过Buffer-Overflow来注入一段代码，并且覆盖掉栈上的返回地址。
* 执行 ret 的时候就会跳转到特定的位置执行代码。

### Data Execution Prevention

* 通过一些手段保证栈、堆标记为不可执行即可，通过权限来防止传统的ROP攻击。

### Code Reuse Attack

* 寻找一系列程序本身的指令片段，特点是 ret 结尾
* Buffer-Overflow时注入多个对应片段的地址，以此来跳转到对应片段进行执行，复用程序本身的指令进行攻击。

### Code Reuse Defence

* 隐藏二进制文件。
* ALSR地址随机化，保证每一次加载程序到内存的时候内存地址是随机的。但是对于Fork创建子进程可能无法很好地工作，因为Fork出的子进程与原进程虚拟内存空间数据分布是完全一致的，如果要在Fork之后再进行一次内存地址随机化，成本很高，因为再次随机化意味着其中很多指针的值就必须得改变。
* Canary：一段在栈上位于Return Address之前的随机数，每次返回时检查返回地址之前的Canary值是否被修改，如果被修改就意味着出现Buffer-Overflow可能会覆盖掉Return Address，以此来防止ROP攻击。

## Control Flow Integrity（CFI）

### 思路

* ROP Attack本质是修改了程序的控制流。在二进制代码中嵌入控制流跳转约束的语义，以防止控制流被篡改。
* 对于间接跳转，嵌入控制流约束；直接跳转的控制流无法被篡改，而间接跳转的控制流是可能被篡改的。
  * Indirect Call
  * Indirect jmp
  * Return
* 在间接跳转指令执行之前，嵌入对间接跳转地址的校验代码。假设知道一个间接跳转指令跳转到的正确地址，就在代码生成时对应的正确地址中插桩一个特殊的 bit pattern 作为 Unique ID 用来作校验，在生成间接跳转的指令之前，插桩一段 cmp 指令比较运行时要跳转到的地址内存位置是否有对应的Unique ID ，如果没有，就说明控制流被篡改。

### 问题

* 兼容性问题，如果是一个添加了CFI机制的库，而原本没有CFI，那么调用这个库的代码有可能直接跳转到已经被插桩Unique ID的位置进行执行（因为只是库做了插桩，调用库的程序没有做插桩，也就不会有对Unique ID的检验逻辑），因为执行一段错误的指令（因为对应的位置是一个数据），就会出错。可以采用一个Prefetchnta来规避这个问题，既插入了Unique ID，而如果要作为指令被执行时又不会出错，当作nop处理。
* 粗粒度的CFI：假设 A 一处间接 call 调 C，B中一处间接 call 可调 C 也可以调 D 的场景，因为A和B都调C，所以A和B中的对应的间接跳转使用的Unique ID是C的Unique ID；而B中同样一处间接跳转指令也可能调用D，在只做粗粒度CFI检验的情况下，D会使用与C相同的Unique ID。因此如果A的间接 call 在运行时被篡改为调用 D ，也会被检验为合法，然而合法的控制流中A对应的那条指令是不会调用D的。同理，对于Return指令也需要做CFI检验，在粗粒度的CFI中，如果A间接调用F，B间接调用F，是有可能出现A间接调用F而返回的控制流被篡改为返回B的，因为A、B的Unique ID需要一致。
* 细粒度的CFI：如果要保证控制流的检验完全正确，就需要保证每一个间接跳转位置的Unique ID唯一。对于一个间接跳转指令，如果正确的控制流中可能跳转到多个位置，那么就意味着在插桩的时候需要加入更多的用于检验的指令，甚至要引入控制流。

## Data Flow Protection & Taint Tracking

### 思路

Taint Tracking对于不可信来源/敏感的数据（用户输入等）进行追踪，在进行敏感操作（通过网络发送用户的隐私数据等）时候发出警告。

* 污点标记：对于输入的数据标记为Taint。
* 污点传播：如果被标记为Taint的数据被复制/参与运算而传递到别的变量，对应的变量也标记为Taint；而对于程序内硬编码的数据则不需要标记为Taint，因为这不是用户输入的数据。
* 污点检测：对于敏感操作，需要对使用到的相关数据检测是否被标记为Taint，如果被标记为Taint则发出警告。

###  问题

* 可以用控制流清洗污点

  ```C++
  if (a == 1){
  	b = 1
  } else if (a == 2){
      b = 2
  } else if (a == 3){
      b = 3
  }
  	…………
  else if (a == 256){
      b = 256
  }
      
  ```

  b作为硬编码的常数值，不会被标记为Taint，而b与a值完全相同，可以清洗掉a的Taint，即用b来进行运算而不使用可能带有污点的a，但是执行效果完全相同，而污点不会被检测到。

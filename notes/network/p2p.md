# P2P

## BitTorrent

BitTorrent希望构建一个p2p的非中心化网络，每个下载文件的节点在下载文件后可以变成提供部分文件下载的节点。

### 角色

* Tracker：是一个中心化的节点，记录所有参与共享的Peers的相关信息。记录 Peers 各自维护哪些文件的哪些部分的节点。
* Seeder：持有整个文件的节点，提供文件的完整数据供以下载，Seeder是特殊的Peer。
* Peer：持有文件的一部分的节点。Peer 可以同时从多个节点下载不同部分的文件，同时也可以向其他节点上传已经下载的部分。文件的传输通过分布式的Peers完成。

### 流程

#### 文件分块

- 上传者将待共享的文件分割成若干固定大小的块，每个块通常为 256 KB 或 512 KB。
- 为每个块计算哈希值，用于后续数据校验，确保块的完整性。

#### 生成torrent file(.torrent 文件)

- **文件的基本信息（如文件名、大小）**。
- 每个块的哈希值。
- **Tracker 地址**，用于引导 Peers 加入共享网络。

#### 发布 `.torrent` 文件

- .torrent是存储元信息的文件，上传者将 `.torrent` 文件上传到共享平台，或者通过 Magnet 链接直接分享给其他人。.torrent文件可以存储在任何地方，不是由Tracker来进行维护的，相反.torrent会指明Tracker。

#### 下载

* 上传者成为Seeder，Tracker中会记录该Seeder
* Peers请求数据时，通过.torrent文件获取到Tracker地址，通过Tracker获取到Seeder以及其他持有该文件部分内容的Peers的位置
* Peers与Seeder/Peers建立P2P连接开始请求文件的某些块来进行文件下载。
* Peers在下载完文件后，可以立即向其他需要这些块的Peers提供下载服务。

#### 问题

* Tracker实际上是P2P网络中一个中心化的节点，如果单一的Tracker故障、被封禁，那么就会失去关于所有Peers的记录。为了让Tracker可扩展性更强，可以采用Distributed Hash Table来存储信息。

## Distributed Hash Table

### 接口

* Put(Key,Value)
* Get(key) → Value
* Loose Guarantees

### 目标

* 希望操作是O(log n)的复杂度。

### 设计

#### Hash Space

* 将要存储的键值对信息中的**键**与存储键值对的**机器节点**哈希到同一个哈希空间中。
* 采用SHA-1哈希函数对Key & Machine Node IP进行哈希得到Key ID & Node ID。
* 如果哈希值大于设定好的哈希空间大小，可以通过取模等方式再进行一次映射。
* **哈希空间是一个闭合的环**。

#### Consistent Hashing

* 由于键和机器映射在同一环形哈希空间，可以将他们认为都是这个哈希空间中的一个节点。
* **每个键都存储在他后继中的第一个机器节点**。（即一个键必定要存储在第一个满足 Node ID > Key ID 的机器节点上）或者可以说，每个键都存储在其沿着哈希环顺时针转遇到的第一个机器节点上。

#### Sequential Lookup

* 在分布式存储哈希的集群中进行特定某个键的查找，必定是通过某一个具体的机器节点，根据该节点持有的关于其他节点的信息来判断下一步跳至哪一个节点进行查询，直到最终找到对应的键。
* 每个节点都保存其前驱机器节点 & 后继机器节点的信息。当在该节点查询一个键时，如果该键节点落在该机器节点与其后继机器节点之间，那么该键必定就存储在这个后继机器节点。
* 通过机器节点前驱后继的关系查询键，时间复杂度是O(N)，在一个有大量节点的集群、P2P网络中是不可忍受的。

#### Finger Table

* 假设在一个哈希空间大小为2^m^的环形哈希空间中（哈希值0~2^m^-1），每个机器节点上维护一张Finger Table，包含m个项目，表中第 i 项是当前机器节点Node ID + 2^i^ 节点所属的机器节点位置(0 ≤  i ＜ m)。相当于记录距离自己1/2环长度、1/4环长度、1/8环长度……一系列位置的后继机器节点。
* 在某个节点上查找键时，~~直接通过Key ID与后继节点Node ID判断后继节点是否持有该键，否则，~~从当前节点的Finger Table中最远处开始向最近处扫描进行查找，直到找到第一个 Node ID ＜ Key ID的机器节点，跳至该节点进行新一轮的查找。对应的时间复杂度是O(log n)。（删除部分应该是一个可能的优化？）

### Successor List & Finger Table

* 如果只依靠Finger Table的跳转方式，如果一个节点最近的若干后继机器节点宕机，导致通过Finger Table的跳转无法跳转到一个Node ID ＜ Key ID的机器上，就可能无法找到对应的键。
* 因此可以在使用Finger Table的基础上，每个机器节点维护一个Successor List，里面存储固定的 r 个最邻近的后继节点，以此来处理机器节点宕机的状况。

#### 节点加入

* 假设节点N~A~的直接后继是N~B~，现在插入一个新的节点N~C~，位于N~A~与N~B~之间
* N~C~的后继节点设置为N~B~，并将N~B~中所有Key ID ＜ Node ID(N~C~)的键值对复制到N~C~中存储，并且N~B~中不会删除对应的内容，通过这种冗余来保证节点宕机退出时的键查询。
* 所有符合条件的键值对从N~B~拷贝到N~C~后，将N~A~的直接后继节点设置为N~C~。（当然如果维护前驱节点指针的话也必须在设置后继指针时一并设置前驱指针）

#### 节点退出

* 节点宕机是不可控的。

#### 虚拟节点

* 在哈希环中有大量机器作为其中的节点分担大量键的存储，可以认为是均匀的。但是实际中构成集群的物理机器很少，这就可能导致键的存储不均匀，意味着每个机器节点承担的负载不均衡，可能存在大量的键通过哈希后都落在同一个机器节点上。
* 引入虚拟节点，在每台物理机器上都抽象出多个虚拟节点参与哈希。比如说，可以在实际只有100台物理机器的情况下抽象出10000个虚拟机器节点来承担大量键存储，通过某种映射将这10000个虚拟节点映射到100台物理机器以达到存储上的负载均衡。
